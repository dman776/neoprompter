# Scroll model

Read this before touching position, speed, Screen jumps, the end-of-Script stop, or the Progress bar.

A Script line is a paragraph and the Output wraps it, so position, speed (lines per second), the viewport, Screen jumps, the end-of-Script stop and Progress are all in visual lines. The Output measures each Script line's height in visual lines after every layout-affecting change and dispatches `setLineExtents { extents, revision }` (like `setViewport`); the core keeps `extents` (1 per line until measured), clamps to `sum(extents) - viewportLines`, and converts the reading position through (Script line + fraction) on edits and re-measures so it stays on the same text. A measurement for an old `scriptRevision` is ignored. The Output is always laid out as a 1920x1080 stage (`src/output/stage.ts`) and scaled to fit its window or monitor (letterboxed, centered), so wrapping, the viewport (`floor(1080 / line height)` lines), line spacing and the reading position never depend on the display. The Operator's Live view draws the same renderer (`src/output/renderer.ts`) on the same stage, scaled, so the top line on the Output is the top line in the Live view (the e2e test checks this at several Output window sizes); it measures only while the Output is not showing (Off or blocked), so time left and Screen jumps work without an Output window. `remainingLines` in core state is the distance from the position to the end-of-Script stop. `scriptRevision` bumps on any Script content change (edit, cut, color, load); the Output re-renders its text DOM on it, not on the Script name.

## Scrolling by hand in the Live view

The Operator can reposition the Script by dragging the text in the Live view (the Run mode one and the mini one in Edit mode), and in Edit mode also with the mouse wheel or trackpad over the mini Live view. In Run mode the wheel does not scroll: it sets the speed (see below). Dragging, and the Edit mode wheel, send `scrollBy` with a number of visual lines: screen px are divided by the Live view's scale and by one visual line's height (`fontSize * lineSpacing`, in stage px), so a drag moves the text exactly as far as the pointer moves. A drag moves the text with the pointer (up goes forward). A playing Script is paused while it is dragged and carries on when the pointer is released, like the ring. A click that moves under 4 px scrolls nothing. In Run mode, with the Script locked, a plain left click in the Live view toggles stop and play (playing, in either direction, stops; stopped plays forward); a drag, a cancelled press, another mouse button, the scrollbar, the Reading line and the Edit mode mini Live view do not. With the Script unlocked a click does nothing, so a double-click can still open a live fix. The Reading line handle is dragged separately and never scrolls the Script.

### The scrollbar in Run mode

The Run mode Live view has a scrollbar down its right edge (`src/operator/ScriptScrollbar.tsx`; the mini Live view in Edit mode and the Output never show one). The thumb sits at `progress` and is one Screen out of the whole Script (never under 8% of the track). Dragging it, or pressing the track, sends `setProgress { progress }`, which puts the reading position that fraction of the way from the start to the end-of-Script stop. A playing Script is paused while the thumb is held and carries on when it is released, like dragging the text. The scrollbar stops the pointer from reaching the Live view behind it, so it never also drags the text.

### Top and End in Run mode

The Run mode transport has TOP and END keys (`src/operator/Transport.tsx`). They send `setProgress { progress: 0 }` and `{ progress: 1 }`: the reading position goes to the start of the Script and to the end-of-Script stop. A playing Script keeps playing (it stops at once at the end, as it always does there). Play start is separate: it returns to the Play start position, not the top.

### The wheel in Run mode

Over the Run mode Live view the wheel changes the speed, not the position: rolling down is faster, up is slower, and one notch (100 px, or 3 lines for a line-mode wheel) is one nudge step (`SPEED_NUDGE_STEP`, 0.1 level). A trackpad's small deltas add up in proportion. It sends `adjustSpeed { levels }`, which clamps like every other speed change. The wheel inside the Virtual shuttle is a different control and still scrolls.

A middle click (the wheel pressed in) in the Run mode Live view toggles the direction (`setDirection`). On a playing Script it turns the Script round without stopping, as Play backward does. On a stopped one it sets the way the next click-to-play goes, and the BACK and FWD lamps show it at once. Pausing, reaching an end of the Script, a restart and loading a Script all put it back to forward, and Play / Pause always plays forward. The scrollbar, the Reading line and the Edit mode mini Live view ignore the middle click, and the press is cancelled so Windows does not start its middle-click autoscroll.

## Playing in reverse

The core plays forward or in reverse (`play` takes an optional `direction`; `CoreState.direction` is `forward` or `reverse`). Reverse plays at the same speed, back toward the start, and stops there. The Play / Pause action (Space by default) plays forward and pauses a Script playing either way; the Play backward action (Shift+Space by default) plays back, pauses a Script already playing back, and turns a forward play round without stopping. Both are Key bindings (below). `direction` is forward whenever the Script is not playing, unless the Operator has set it with a middle click (`setDirection`, below); a pause, an end of the Script, a restart or loading a Script puts it back to forward. The ring still adds to whichever way it plays. The Run mode transport shows it as BACK and FWD.

## Key bindings

A Key binding gives an action a key (a physical key, `KeyboardEvent.code`, with any Shift, Ctrl, Alt and Cmd held). The actions are Play / Pause, Play backward, Back a Screen, Forward a Screen, Play start, Speed up, Speed down and Dismiss Notification; each can have several keys and a key belongs to one action. The table, its rules (Esc, Tab and the menu's keys are refused; a key another action has is moved only on request) and its file (`key-bindings.json`) are in `src/input/keyBindings.ts` and the main process owns it; the Operator view reads the same table, so a change in Preferences works at once. The defaults are the keys the prompter always had: Space, Shift+Space, the Up and Down arrows, the Left and Right arrows and Page Up and Page Down.

A binding runs its action on key down, only in the Operator view's Run mode with the Script locked, and never while a text field has focus; Edit mode has none. Holding a key repeats only Speed up and Speed down. Holding Shift with a Speed up or Speed down key that has no binding of its own makes the bigger step (`resolveKey`). The ring and the jog wheel are not bindable: a key is a tap, with no release to end a hold. See [shuttlexpress.md](shuttlexpress.md) for using a ShuttleXPress through its driver software.
